# Learnings

Technical discoveries that should persist across sessions.

## React-Leaflet rendering

- **`react-leaflet@4.x`'s `<Polyline>` only flows `pathOptions={...}` updates to Leaflet's `setStyle()`.** Top-level `color`, `weight`, `opacity` props are spread into the polyline at *creation* time and **silently ignored on re-render**. If a Polyline's color depends on prop state that changes (e.g. tier color recomputed when the user switches travel mode), pass styling via `pathOptions` or React will keep the old stroke painted on screen forever. The data layer (route panel, quality bar) updates correctly because it's plain React; the painter stale-renders because Leaflet's mutable layer didn't get the memo. Caught launch-day 2026-04-29 — bar showed 15% medium-green for "Living street" segments while the polyline kept them orange from the prior mode.
- **The bug class is "rendering-layer divergence" — same data, different surfaces disagree.** Pure-script reproductions (`scripts/debug-color-mismatch.ts`) cover the data path but miss bugs in the React → Leaflet bridge. To reproduce these, drive the actual UI in the browser (claude-in-chrome MCP works for this) and compare what the bar/legend says against what the painted DOM shows. If they disagree, the bug is downstream of the data computation.

## Scoring architecture

- **One classifier drives both display and routing.** The same function that colors map tiles green or orange is the function that builds the routing cost function. Two parallel classifiers drift silently; a single source of truth does not. In this repo the canonical function is `classifyOsmTagsToItem` (for display) + `classifyEdge` (for routing), and the PR review should confirm neither grows mode-specific logic that diverges from the other.
- **A routing input must be mirrored to the overlay, or the map advertises what the router avoids.** The BRouter-style ascent cost (PR #192) made the router route *around* steep hills, but the browse overlay had no elevation awareness — so a 22% `highway=path` hiking trail still painted as preferred green "Bike path." Same class as classifier drift: routing and display disagreed because a signal lived in only one of them. Fix (2026-06-02): the per-way ascent sum is now a single shared helper (`wayAscentMeters` in `elevation.ts`) consumed by both the router's A* cost and the overlay's `overlayGradientPct` steepness gate. When you add a new cost input to routing, check whether the overlay needs the same gate — `bun` a quick classify-over-real-OSM diagnostic (fetch a tile, run the production functions, bucket the output) before assuming the map already reflects it.
- **Overlay "confetti" is usually a zoom-floor change, not new data.** "Weird short segments all over SF, now" traced to PR #175 dropping `OVERLAY_MIN_RENDER_ZOOM = 12` — at city-overview zoom every tiny `footway=crossing` / `cycleway=crossing` stub (one per intersection) now paints. They're real routing connectors but visual noise on the browse map; `isOverlayCrossing` hides them from display only. When the overlay suddenly looks busier, suspect a visibility/zoom-gate edit before suspecting the data.
- **Speed-based costs beat arbitrary penalty multipliers.** The router computes edge cost as `distance / speed`, where speed depends on infrastructure and mode. This naturally makes walking bridges (3 km/h on a sidewalk) cheaper than a 200 m detour through traffic without any special-case logic. Penalty-multiplier schemes like "painted lane is 3× worse than Fahrradstraße" are harder to tune and don't compose cleanly with multimodal bridges.
- **`highway=track` (forest/farm track) is LTS 1 + car-free for routing purposes** in `classifyEdge`, matching pre-refactor behaviour. Motor traffic exists but is rare and agricultural — different enough from a residential street that treating it as car-free is the least-surprising default. If this becomes wrong in a specific city, demote in the Layer 2 region overlay rather than changing the global rule.
- **The `carFree` vs `bikePriority` distinction on `LtsClassification` is load-bearing.** `carFree` means the bike does not share a traffic surface with motor vehicles (cycleway, path, curb-separated cycle track). `bikePriority` means the bike shares the surface but the street is engineered to give bikes priority (Fahrradstraße, SF Slow Street, living street). Kid-starting-out accepts either; kid-confident additionally accepts ordinary quiet residential. Don't collapse the two flags into one — they express different real-world guarantees.
- **SF Slow Streets appear in OSM as `highway=residential` + `motor_vehicle=destination`**, not as a dedicated tag. This is the OSM convention for "local-access only, through-traffic diverted" and is how `classifyEdge` detects them.

## Diagnosing routing regressions

- **Ablate cost components before trusting a hypothesis about which one caused a regression.** When a route "goes the wrong way," the instinct is to name a cause (turn penalty, stop signs, …) and tune it. That's how the 2026-06-12 turn-cost handoff sent us at the wrong fix for a full session. The reliable method: build the graph, then route the SAME pair with each cost term zeroed in turn (a script that mutates the in-scope `ModeRule` / passes `elevationFn=null` and re-routes), and watch which ablation actually changes the route. For the Buena Vista + JFK regressions, zeroing turn/signal/stop costs changed *nothing*; only zeroing **ascent cost** moved either route. Cost-attribution by ablation is ~10 lines and 30 seconds and it beats any amount of reasoning about which term "should" dominate. Pattern lives in `scripts/diag-turn-cost-ablate.ts`.
- **Walking (bridge-walk) edges were silently exempt from ascent cost** (`useAscentCost = !isWalking`), which let A* take the steepest, shortest dismount straight up a hill rather than ride a flatter, longer route — kid-confident walked up Buena Vista Park instead of riding the flat Wiggle. A "free" cost loophole on one edge class distorts route choice in non-obvious ways. Fixed 2026-06-20 by charging walking ascent the same per-metre rate; benchmark confirmed it didn't break the bridge-walk connectivity invariant. When adding a cost term, check it applies to EVERY edge class it should, not just the obvious one.
- **`carFreeBonus` expresses "families prefer car-free even if longer" as a tunable cost discount, not a hard rule.** Time+ascent cost alone makes carrying-kid/training pick a shorter, flatter arterial over the longer car-free JFK Promenade — technically optimal, not what families want. A per-mode `<1` multiplier on `classifyEdge.carFree` edges (physical separation only; Fahrradstraße/living-street do NOT qualify — they're `bikePriority`, not `carFree`) nudges the preference without forcing absurd detours. Strength scales with the mode's LTS ceiling (carrying-kid 0.7 … kid-starting-out 0.9). It raises benchmark preferred-% as a side effect, which is the right direction.

## Mode rules

- **Stamina is orthogonal to safety.** Earlier drafts of `ModeRule` carried a `maxContinuousKm` cap that rejected routes longer than a distance threshold. This conflates two axes: "this infrastructure is safe" and "my kid can ride this far before getting tired." Families judge distance themselves. The router optimises safety + time; distance is a user choice.
- **Fahrradstraßen ride at `ridingSpeedKmh`, NOT `slowSpeedKmh`.** A previous draft applied the caution slowdown to all non-car-free LTS 1 edges and broke routing — kid-confident rode Fahrradstraßen at 5 km/h while cycleways were at 10 km/h, so the router detoured onto any cycleway to escape them. The fix gates the slowdown on `!carFree && !bikePriority`, so ordinary quiet residential still drops to slowSpeedKmh but Fahrradstraßen, living streets, and SF Slow Streets run at full riding speed — reflecting their engineered-for-bike-priority design.
- **Rejected edges become bridge-walks, not drops.** When `applyModeRule` says "this edge is too stressful for this rider," the graph builder does NOT remove it — it re-adds it as an edge at `walkingSpeedKmh` with `isWalking: true`. The rider dismounts and walks the bike on the sidewalk. Speed-based cost makes walking very expensive per metre, so A* only uses these as short unavoidable bridges, but crucially the graph stays connected. The alternative (hard-reject) turned kid-confident into 5/22 routes across Berlin because most central trips need to cross at least one Hauptstraße. Hard-rejection is reserved for motorway/trunk and roads with explicit `sidewalk=no` — places there is genuinely nowhere to put your feet. See `isBridgeWalkable` in `clientRouter.ts`.
- **Kid-confident must be a strict surface superset of kid-starting-out.** The display classifier's `isBadSurface` previously flagged `paving_stones` as "Rough surface" for all modes except kid-starting-out. Paving stones are Berlin's standard bike-path material, so toggling from starting-out → confident turned most bike paths from green to orange — users perceived it as "kid-confident sees less preferred infra than kid-starting-out," the opposite of the intended hierarchy. Fix: treat paving stones as fine for both slow kid modes; only the higher-speed modes (traffic-savvy, carrying-kid, training) still flag them as rough. The invariant is that as kid skill increases, the accepted set grows monotonically — any break in that monotonicity confuses the user.

## Elevation / terrain data

- **Local dev can NEVER load terrain-RGB tiles — elevation-dependent features are inert on localhost.** `VITE_MAPBOX_TOKEN` is URL-restricted to `https://bike-map.fryanpan.com/`; browsers refuse to override the `Referer` header, so every terrain fetch from a localhost dev server 403s and caches as fetched-and-failed. Everything correctly fails soft (gradients null → all ways shown, no ascent cost), which looks exactly like "my steepness feature doesn't work." Verify with (a) a `bun` script that calls `setElevationReferer('https://bike-map.fryanpan.com/')`, or (b) prod after deploy. Discovered 2026-07-02 during steep-moat filter verification.

## Overlay rendering

- **Per-way visibility gates shred networks into white-halo confetti.** Any gate that hides ways individually (steepness, moat) interacts with the gradient noise floor: ways shorter than `MIN_GRADED_LEN_M` return null gradient and fail-soft SHOWN. When the long ways around them get hidden, the surviving stubs paint a white halo (weight+4, round caps) around a thin colour core — at browse zoom that reads as white pills, not paths. This is why the steep-moat filter (#208) was reverted (#209) on 2026-07-02. A re-land must give sub-floor stubs a component-level verdict (inherit the hidden/shown decision of their graph context), not an individual fail-soft.
- **`GoogleMapsEngine.addPathLayer`/`removePathLayer` race leaks deck.gl layers permanently.** `addPathLayer` registers the layer in a `.then` (async deck import); `removePathLayer` early-returns when the id isn't registered yet, so a remove that races the pending add leaves the layer painted forever — visible as double-plotted geometry at stale zoom simplifications, compounding GPU cost over the session. The window is widest during initial deck.gl chunk load; startup main-thread work amplifies it. Fix direction: tombstone removed ids so the pending `.then` skips the add. Unfixed as of 2026-07-02.
- **Overlay-wide computation must stay off the tile-arrival hot path.** #208 ran union-find + per-vertex gradient lookups over EVERY fetched way (streets included, ~10× the painted set) synchronously on every tile arrival and elevReady bump — visible jank at metro zoom. Re-land constraint: compute per tile-set generation on idle, restrict to painted candidates, and cache null gradient results (not just non-null) keyed by elevation generation.
- **Browser verification must falsify, not confirm.** The #208 browser pass checked *for* the intended effect (Marin decluttered) and looked straight past two obvious new artifacts visible in the verification screenshots themselves. The check that identified the white pills afterwards took 30 seconds: click the odd-looking thing and read its popup. UI verification of overlay changes needs an explicit "what looks NEW and wrong vs. before?" pass at multiple zooms, not just the feature's acceptance criteria.
- **Two screenshots of the same viewport that differ over time ARE a finding, not "progressive loading."** During the 2026-07-11 activation pass, screenshots 10 s apart showed different overlay paint and it was read as tiles still loading. Loading only ADDS paint; anything that REMOVES already-painted edges without user interaction is a regression. Time-dependent rendering bugs are invisible to any single static screenshot; verification needs a same-viewport t0 vs t+15s stability comparison (now mandated by `.claude/rules/rendering-changes.md`). Note the designed exception: RAW (non-enriched) ways fail-soft SHOWN until terrain arrives, so steep ways "pop out a beat later" by design — enriched ways carry synchronous verdicts and must never flicker.

## OSM tag units and defaults

- **`parseInt(tags.maxspeed)` is always wrong outside Europe.** OSM stores US/UK speeds unit-suffixed (`maxspeed=25 mph`); `parseInt` returns `25` and every downstream km/h comparison then treats a 40 km/h street as a 25 km/h one. In central SF **every single** `maxspeed` value in the painted-lane corpus is mph-suffixed — there are zero bare-numeric values — so this wasn't an edge case, it was the whole city. The error runs in the dangerous direction for a family-safety product: 85 ways posted `30 mph` (48 km/h, an arterial) were classifying as "Painted bike lane on quiet street." Parse units explicitly (`parseMaxspeedKmh` in `lts.ts`); handle `mph`, bare km/h, `walk`, `none`, and return null for anything else rather than guessing.
- **A units bug and a mis-calibrated threshold can cancel out, so fixing either one alone makes the product worse.** SF's blue "quiet street" tier existed *only* because mph values were being read low enough to slip under a 30 km/h ceiling — 301 of its 338 ways got there that way. Fixing the parse in isolation would have collapsed the tier to 46 ways and looked like a catastrophic regression; raising the ceiling in isolation would have left 30 mph arterials mislabelled as quiet. Before shipping half of an entangled pair, measure what the *other* half is currently compensating for.
- **A road-class speed default is a guess, but a threshold treats it as a measurement.** `derivePathLevel` fails open when `speedKmh` is null (car-free paths) but fails closed on a road-class fallback — so an untagged `tertiary` inherited a confident 50 km/h and dropped below the overlay's preferred set entirely. Net effect: **pathLevel 2a was unreachable for any way of class tertiary or above unless a mapper had typed an explicit `maxspeed ≤ 30`.** Berlin hid this because it tags 99% of its tertiaries (413/417); SF leaves 137 of 210 untagged, which is why Folsom St and 17th St painted nothing. When a heuristic default feeds a hard gate, check what fraction of the corpus actually carries the real tag before trusting the gate.
- **Verify a threshold change against every city you already serve, using live OSM, before calling it safe.** Moving the 2a ceiling 30 → 40 km/h sounded like it should loosen Berlin. It changes **zero** Berlin ways — Berlin streets are posted 30 or 50 and nothing sits in between. That measurement is what made a global threshold defensible instead of forcing a per-city classification path (which would have re-introduced classifier drift, since city profiles can only override the *display* item name, not `classifyEdge`). `scripts/diag-2a-reachability.ts` is the reusable form of this check — run it for any new city.

## OSM tag coverage

- **`width` / `est_width` on cycleways is too sparsely tagged to be actionable.** Bryan asked 2026-04-23 whether we should filter routes by minimum path width for kid-starting-out. Spot-checks of Berlin's cycleway corpus showed single-digit percentages of ways with a `width=*` tag — most paths have no width data at all. A width filter would only catch the minority that ARE tagged narrow, create visible inconsistency ("this unmarked one is fine but that 1.2 m one is rejected?"), and drive very little routing change. Decision: keep width unread by the router; revisit only if OSM coverage materially improves (or if a city-specific profile wants to override for a specific corridor with known tagging). Similar reasoning applies to `lanes=*` on cycleways.

## Router cleanup

- **Valhalla and BRouter are benchmark-only.** They live in `src/services/benchmark/` with explicit "BENCHMARK ONLY" comments and are imported only by `routerBenchmark.ts` and `AuditEvalTab.tsx`. The main app path goes through `src/services/clientRouter.ts` exclusively. If you need to add a feature that seems to require Valhalla (e.g. multi-waypoint routing), chain `clientRoute` calls inline instead.
- **Waypoint routing works by inline-chaining `clientRoute` calls** in `App.tsx` and concatenating the results, rather than delegating to a waypoint-capable router. Each leg is independent; leg boundaries just drop the duplicate joint coord.
- **`useRoads` is dead.** It was a Valhalla-specific costing knob that lived on `LegendItem` and was computed from the user's preferred items via `getCostingFromPreferences`. When Valhalla left the main path, both disappeared. If you see a reference to `useRoads` outside `benchmark/`, it's a stale comment.
- **Nearest-node snap must be role-aware AND reachability-aware** in a directed graph. `findNearestNode` originally picked the geometrically-nearest node with any edge. For start nodes that's fine, but for end nodes, an upstream-of-one-way node has outgoing edges but zero incoming — A* can't arrive there. Worse: some nodes have incoming edges but land on a tiny directed island that isn't directed-reachable from the start. Fix: (a) pass `role: 'start' | 'end'` and require outgoing-for-start / incoming-for-end; (b) pre-compute the directed-reachable set from the start node via BFS (O(V+E)) and restrict the end-snap to that set. Without (b), ~23% of benchmark samples (45/195 in 10fb94a — 41% of SF) returned NULL even though a viable endpoint existed 20–100 m away. The directed islands come from multiple causes — one-way streets, `continue`'d motorway/trunk edges, and (biggest) the Overpass query only fetches bike-relevant highway tags (cycleway, residential, living_street, path, track, footway, plus any road tagged with a cycleway lane/track). Tertiary/secondary/unclassified streets without cycleway tags aren't in the graph at all, creating gaps across corridor streets in cities like SF where bike-tag coverage is sparser than Berlin.

## Shipping / deploy

- **Ship the rollback lever in the same PR as the activation lever.** Landing `upload-tiles.ts --rollback-to` alongside the manifest activation enabled a 5-minute prod A/B that settled a suspected rendering regression empirically. When a PR turns something on in prod, include the one-command off switch in the same PR — it converts "argue about whether prod got worse" into a 5-minute experiment.
- **`bun run deploy` from a local machine stamps prod with `APP_VERSION=0.0.0-local` and clobbers CI's properly-versioned deploy.** deploy.yml (push to main) injects the real version; the local script doesn't. On 2026-07-11 a manual deploy landed ~40 s after CI's and won the race — Sentry releases and userback telemetry were mistagged until a CI rerun (`gh run rerun <deploy-run-id>`) restored it. Never `bun run deploy` for a mainline release; let CI deploy, or rerun the deploy workflow. Manual deploys are for emergencies only, followed by a CI rerun.
- **A prod bug report must be version-checked before it's treated as a live regression.** Bryan's 2026-07-11 "performance is bad and the disappearing edges are back" traced to his iOS Home-Screen bookmark pinning an earlier app version — fresh web loads showed neither symptom. iOS standalone (Add to Home Screen) web apps cache the shell aggressively and don't obviously refresh. Before diagnosing, confirm the client's `APP_VERSION` matches the current deploy (ticket open for surfacing version + update prompt in-app).

## Enriched tiles (prod operations)

- **Manifest rollback is a 60-second prod A/B switch — use it to falsify "is this new-wrong or old-wrong?"** The Worker serves enriched tiles only when R2 `manifest.json` names an active version, and `upload-tiles.ts --rollback-to <v>` rewrites only the manifest (live within the 60 s Worker cache TTL). Rolling back to a *nonexistent* version forces full fail-open to the Overpass proxy — the exact pre-enrichment code path. During the 2026-07-11 activation the mid-zoom overlay looked suspiciously sparse; instead of reasoning about it, rollback → reload → replay the same clicks showed the identical sparse pattern on the old path (pre-existing display behavior, not a regression), then rollback-to the real version restored enrichment. Zero deploys, zero tile re-uploads, whole A/B ≈ 5 minutes.
- **A bodyless GET to `/api/overpass` returns an Overpass 400 ("input contains only whitespace") — that's your probe being malformed, not a broken proxy.** The route forwards the request body as the Overpass query; the real client always POSTs. Non-OK responses are NOT edge-cached (`resp.ok && !isPartial` gate), so diagnostic probes can't poison a tile key — but use a POST with a real query if you need to exercise the true fallback path.

## Stacked PRs

- **Squash-merging the base branch makes a stacked PR DIRTY**, not CLEAN. GitHub sees the squash commit on main as a brand-new SHA that doesn't match the original commits in the stacked branch, and reports conflicts for every file both touch. The fix is to merge `origin/main` into the feature branch, resolve conflicts by `git checkout --ours` (the stacked branch's content supersedes the squashed base by definition), commit the merge, and push. This was how PR #111 was cleanly merged after PR #110 squashed.

## Render-check harness (scripts/render-checks/)

- **`wrangler dev` persists R2/D1/cache state to `.wrangler/state/` on disk across process restarts** within the same worktree — it is NOT a fresh Miniflare instance every run. Building an automated check that measures "how much does the overlay paint on a cold load" against a `wrangler dev` server without accounting for this measures the WARM-cache number, which can be 8x+ higher than a genuine first-ever run (measured 2026-07-11: an SF viewport read 3000+ painted px warm vs. ~360 cold). `.wrangler/` is gitignored so real CI/fresh-checkout runs are always cold — calibrate against `rm -r .wrangler/state/v3/cache .wrangler/state/v3/r2` + a fresh run, not whatever number a repeatedly-poked local dev server gives you.
- **This machine runs several other long-lived local services on conventional dev ports** — a live-feedback plugin server was found squatting on port 8787 (wrangler's own default), silently answering any harness that just checks "did *something* respond" on that port. A port-readiness check that only verifies "got an HTTP response" cannot detect this; it must verify the response body actually belongs to the app under test (e.g. checking for a distinctive `<title>` string) before declaring the server ready.
- **Playwright's `waitUntil: 'networkidle'` is too strict for an app with any background polling** (analytics beacons, or — here — the overlay's own cascading per-tile Overpass fetches at wide zoom). It throws on timeout rather than degrading, so a hard dependency on it turns one slow scenario into a full check failure. Treat it as best-effort (`.catch()` + a warning), and prefer a check tied to the app's own actual "are we still loading" signal (the render checks poll `.tile-loading-boxes`, `src/components/TileLoadingBoxes.tsx`, going hidden) over a generic network-quiescence heuristic.
- **A single slow/retrying tile can keep an "is anything loading" indicator active indefinitely**, even after every other tile has resolved and painted — observed the painted-pixel count stabilize by ~10s while `.tile-loading-boxes` stayed attached for 90s+ in the same run. A settle-wait built on "wait for zero in-flight work" should cap itself and treat the timeout as expected background noise, not a stall — waiting for a hard zero just makes every check as slow as the single worst tile, for no accuracy gain past the real convergence window.
- **HSL saturation is not a reliable "is this pixel part of the vivid overlay, or the muted basemap" heuristic** — OSM Carto's own pale road fills (`#fcd6a4`) have HSL saturation ~0.94 despite reading as washed-out pastels, because HSL saturation isn't lightness-normalized. Matching against the small, known overlay tier palette (`colorForLevel`'s actual output colors, imported from `src/utils/lts.ts` / `classify.ts` so it can't drift) with an RGB-distance tolerance for antialiasing avoids this false-positive class entirely.

## Research documentation

- **Every city-profile claim cites a source URL**, non-negotiable. When research agents return findings without URLs, treat the finding as "unverified" and either ask for sources or drop the claim. The `docs/research/family-safety/city-profiles/` tree is structured so every bullet can be traced back to a named source: advocacy org, government plan, academic paper, or named blog/journalist. This is the defence against "AI slop" in a research-heavy product.
- **LTS framework is anchored to [Peter Furth's canonical criteria page](https://peterfurth.sites.northeastern.edu/level-of-traffic-stress/)**. When in doubt about how to classify an edge, consult that page before changing `classifyEdge` or any `ModeRule` threshold.
